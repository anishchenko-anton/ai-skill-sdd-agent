# Angular Best Practices & Architectural Rules (`docs/angular-rules.md`)

Данные правила применяются агентом **по требованию** при разработке, рефакторинге и генерации кода на фреймворке Angular.

---

## 1. Архитектура шаблонов (HTML & Styles Isolation)
Шаблоны компонентов (HTML) должны всегда выноситься в отдельные файлы (например, `name.component.html`), а не инлайниться внутри `.ts` файла. В декораторе `@Component` обязательно использовать `templateUrl` вместо `template` и внешние стили (`styleUrls` / `styleUrl`).
- **Исключение**: Допускается инлайновый шаблон только для сугубо микроскопических оберток из 1-2 строк текста.

## 2. Максимальное переиспользование (DRY)
Вся архитектура фронтенда должна проектироваться с расчетом на переиспользование. Повторяющиеся UI-элементы (карточки, кнопки, панели) обязаны выноситься в отдельные "тупые" (dumb/presentational) Angular-компоненты или глобальные стили (`@apply` в стилях), исключая дублирование HTML-разметки и длинных цепочек стилей.

## 3. Централизация дизайн-токенов (Design Tokens)
Любые стилевые константы (цвета, скругления, тени, толщина рамок) строго запрещено хардкодить в классах (например, `rounded-[20px]`). Они обязаны выноситься в конфигурацию темы (Tailwind/CSS Variables) в виде семантических переменных. Конфиг темы выступает единым источником правды для дизайн-системы.

## 4. Работа с иконками (SVG Sprites)
Строго запрещено дублировать простыни инлайн SVG-кода в шаблонах. Все интерфейсные иконки должны выноситься в единый SVG-спрайт (`assets/icons.svg`) внутрь тегов `<symbol>`. В HTML-компонентах иконка вызывается по ссылке:
```html
<svg class="w-5 h-5"><use href="assets/icons.svg#icon-name"></use></svg>
```

## 5. Локализация (i18n & Transloco)
Для многоязычности интерфейса используется библиотека **Transloco** (`@ngneat/transloco`) для динамического переключения языка в рантайме без перезагрузки страницы. Все переводы хранятся в JSON-файлах.

## 6. Поведение модальных окон (Modal Backdrop Click & Escape)
Любые модальные окна проекта обязаны поддерживать закрытие при клике на оверлей/бекдроп за пределами контента окна (`event.target === event.currentTarget`), а также по нажатию клавиши `Escape`.

## 7. Обязательные уведомления о результате операций (Feedback Toasts)
Любые пользовательские действия, связанные с сохранением, созданием, изменением или удалением данных (HTTP POST, PATCH, PUT, DELETE), **ОБЯЗАНЫ** визуально подтверждаться всплывающими уведомлениями (тоастами/баннерами) с явным указанием результата: успех (`success`) либо ошибка (`error`). Пользователь никогда не должен оставаться в неведении о статусе операции.

## 8. Переиспользование переводов (i18n DRY)
При добавлении текстов строго запрещено создавать дублирующие ключи переводов для одинаковых терминов и действий ("Сохранить", "Удалить", "Отмена", "Статус"). Общеупотребительные слова обязаны браться из общего верхнеуровневого блока `COMMON.*` в JSON-файлах переводов. В специфичные блоки модулей добавляются только узкоспециализированные термины.

## 9. Использование сигналов и реактивность (Angular Signals for Reactivity)
Вся реактивность фронтенда и состояние сервисов и компонентов должны реализовываться строго на нативных **Angular Signals** (`signal()`, `computed()`, `input()`, `output()`).
- Запрещено создавать новые `BehaviorSubject` или `Subject` для хранения состояния.
- RxJS используется исключительно для асинхронного сетевого взаимодействия по HTTP/WebSocket (с конвертацией в сигналы через `toSignal()`).
- В шаблонах HTML обращение к состоянию производится через вызов сигнала: `{{ myValue() }}`.

## 10. Запрет моков внутри компонентов и сервисов (Data Architecture & Services)
- **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** хардкодить моковые бизнес-данные внутри сигналов и полей компонентов или сервисов.
- **Сервисный слой (Data Access)**: Компоненты должны быть чистыми презентационными сущностями. Все данные ДОЛЖНЫ получаться из Angular Services через `HttpClient` / REST API бэкенда.
- **Обработка отсутствия бэкенда**: Если API еще не реализован на бэкенде, создается эндпоинт/контроллер на бэкенде либо фикстура/интерцептор (`HttpInterceptor`), реализующий контракт.
- **Начальное состояние сигналов**: Сигналы компонентов и сервисов инициализируются состоянием загрузки/отсутствия данных (`null`, `undefined` или `signal<DataModel | null>(null)`).

## 11. Единая архитектура карточек и виджетов (Unified Card Wrapper)
- **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** создавать виджеты/карточки с обособленной версткой заглавной панели без стандартных контролов.
- Все карточки и виджеты оборачиваются в единый переиспользуемый Angular-компонент карточки (например, `<app-dashboard-card>`).
- Стандартизированные элементы: унифицированный заголовок, иконка, слот под статусные действия (`card-header-actions`) и контрол закрытия/сворачивания.

## 12. Единая архитектура модальных окон (Unified Modal Wrapper)
- **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** дублировать разметку затемнения фона (`fixed inset-0`) в фиче-компонентах диалогов.
- Все диалоги и формы обязаны использовать переиспользуемую обертку модального окна (например, `<app-modal>` / `<app-confirm-modal>`).
- Это гарантирует 100% централизацию обработки оверлея (`mousedown` + `click`), клавиши `Escape`, анимаций и оформления.

## 13. Инкрементирование версии фронтенда (Automatic Version Bump)
При функциональных изменениях фронтенда перед коммитом обновляется patch-версия / build number:
- В `frontend/package.json`.
- В `frontend/src/environments/environment.ts` и `environment.prod.ts`.

## 14. Документирование методов и функций (TSDoc / JSDoc "Why/What/For What")
Каждый публичный и приватный метод в сервисах, компонентах, пайпах и гвардах обязан содержать TSDoc/JSDoc комментарий:
- **Назначение (Для чего)**: Какую задачу решает метод в контексте UI или состояния.
- **Логика (Что делает)**: Описание параметров, преобразований потоков и возвращаемого значения.
- **Обоснование (Почему)**: Почему выбран конкретный подход (например, почему здесь `untracked()`, почему debounce именно 300ms, почему отписка через `takeUntilDestroyed`).

## 15. Стандартизация импортов и Path Aliases (@-Imports / No Relative Hell)
- **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать длинные цепочки относительных выходов (`../../environments`, `../../../core/services/...`).
- Для всех межмодульных импортов **ОБЯЗАТЕЛЬНО** использовать настроенные TypeScript path aliases из `tsconfig.json`:
  - `@env/*` — конфигурации окружения (`@env/environment`).
  - `@app/*` — корневой уровень приложения (`src/app/*`).
  - `@core/*` — синглтон-сервисы, интерцепторы, гварды (`src/app/core/*`).
  - `@shared/*` — общие компоненты, модалки, пайпы, типы (`src/app/shared/*`).
  - `@features/*` — модули страниц и фичей (`src/app/features/*`).
  - `@layout/*` — компоненты структуры и лейаутов (`src/app/layout/*`).
  - `@auth/*` — аутентификация и сессии (`src/app/auth/*`).
- **Исключение**: Относительные пути (`./child.component`, `./name.model`) разрешены **исключительно** внутри одной и той же директории для соседних тесно связанных файлов. Любые выходы наверх (`../`) используют `@`-алиасы.
