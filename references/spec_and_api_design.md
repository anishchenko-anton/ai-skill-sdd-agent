# Фазы 1-3: Концептуальный фильтр, Архитектурная трассировка и Spec-First

Данный регламент определяет протокол нисходящей подготовки задач (Architecture-First Top-Down Funnel): от абстрактной модели к сквозному физическому пайплайну и формализации спецификаций.

---

## 1. ФАЗА 1: Концептуальный фильтр (`docs/ABSTRACT.md`)

Перед созданием любого предложения или изменением кода агент **ОБЯЗАН** проверить соответствие задачи глобальной концептуальной модели в `docs/ABSTRACT.md`:

1. **Доменные сущности и границы (Domain Entities & Bounded Contexts)**:
   - Идентифицировать сущности, затрагиваемые задачей (например: Room, User, Device, StreamSession, DeviceShadow).
   - Проверить, не нарушается ли граница ответственности домена.
2. **Модель прав и матрица авторизации $P(S, A, R, C)$**:
   - $S$ (Subject / Актор): кто инициирует действие (Guest, Operator, Admin, System).
   - $A$ (Action / Действие): что именно выполняется (Read, Control, Takeover, Modify).
   - $R$ (Resource / Ресурс): над чем выполняется действие (Room, Device, Telemetry).
   - $C$ (Context / Контекст): при каких условиях (в активной комнате, при наличии токена, в рабочем статусе).
3. **Системные инварианты (System Invariants)**:
   - **Single Source of Truth (SSOT)**: Где хранится каноническое состояние? Исключить дублирование состояния.
   - **Fail-Safe**: Каково безопасное состояние при обрыве связи или отказе (например, переход в Read-Only, сброс управления)?
   - **On-Demand Laziness**: Ресурсоемкие процессы (WebRTC, WSS стриминг, аппаратный опрос) запускаются строго по требованию потребителя и глушатся при отсутствии слушателей.
   - **Device Shadow**: Состояние оборудования синхронизируется через теневой объект; одновременное управление несколькими операторами блокируется (Single Control Owner).

## 2. ФАЗА 2: Трассировка физической цепочки (`docs/ARCHITECTURE.md`)

После подтверждения концепта агент **ОБЯЗАН** проследить сквозной физический путь прохождения данных по `docs/ARCHITECTURE.md`:

1. **Сквозной поток данных (E2E Data Flow)**:
   - Определить полный маршрут: `UI Component (Signals) -> Network Transport -> Gateway/Controller -> Guard/Policy -> Application Service -> Domain Model -> Protocol Driver / ORM -> DB / Hardware`.
2. **Транспорт и протоколы взаимодействия**:
   - **WebSocket / Socket.IO (WSS)**: Real-time команды, сигналинг, обновления состояний.
   - **WebRTC / WHEP**: Низколатентный видеостриминг (MediaMTX).
   - **REST API**: CRUD-операции, авторизация, управление ресурсами.
   - **UDP / Serial (MAVLink, CRSF)**: Прямое телеметрическое и командное взаимодействие с контроллерами (ESP32/STM32).
3. **Зоны ответственности и отказоустойчивость**:
   - Где обрабатываются таймауты и дисконнекты?
   - Какие гварды (Guards / Interceptors) валидируют запрос на входе?

## 3. ФАЗА 3: Спецификация и унифицированный RESTful API (Spec-First)

1. **Правило нулевого кода (Zero-Code Rule)**: Категорически запрещено создавать или модифицировать файлы исходного кода до тех пор, пока спецификация не задокументирована в `.openspec/` и не согласована.
2. **Артефакты спецификации**:
   - Расположение: локальная папка модуля `src/app/modules/<name>/.openspec/specs.md` (или корневая `.openspec/specs.md`).
   - Формат: Given-When-Then / Поведение состояний / Описание DTO.
   - **Запрет на код в спеках**: Спецификации описывают бизнес-поведение, а не программный код.

### Унифицированный стандарт RESTful API
- **URL**: Множественное число, kebab-case (`/api/v1/devices/{id}/telemetry-sessions`).
- **Глаголы**: `GET` (чтение), `POST` (создание), `PATCH` (обновление), `DELETE` (удаление).
- **Ошибки по RFC 7807 (Problem Details)**:
```json
{
  "type": "https://api.domain.com/errors/validation-error",
  "title": "Invalid Request Payload",
  "status": 422,
  "detail": "Field 'roomId' is invalid.",
  "errors": [{ "field": "roomId", "message": "Room not found or inactive" }]
}
```

## 4. Проектирование слоя абстракции (Extensibility & Decoupling)

При создании Proposal и Design для любых новых сущностей или сервисов агент **ОБЯЗАН** закладывать слой абстракции:

1. **Интерфейсы контрактов (Ports)**: Доменная логика зависит от абстракций (`IDeviceControlPort`, `IStreamProvider`), а не от конкретных SDK/библиотек.
2. **Изолированные адаптеры (Adapters)**: Драйверы протоколов и БД реализуются отдельно (`MavlinkAdapter`, `TypeOrmRepository`), обеспечивая безболезненную замену в будущем.
